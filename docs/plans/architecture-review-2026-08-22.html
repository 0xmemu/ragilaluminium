STRONG

Kandidat A — Perdalam "pengaturan tampilan" menjadi 1 modul (bukan 14 shallow)

app/Support/*Settings.php (14 file, total 2854 baris, rata-rata ~204/klas)

Problem: Ada 14 kelas shallow berpola (AnnouncementSlideSettings, FlashSalePeriodSettings, CaraPemesananSettings, dll.), masing-masing hanya bungkus getter dari `cms_pages` content. Interface-nya hampir serumit implementasi → menerapkan deletion test: menghapus semua 14 lalu menggabungnya memusatkan kompleksitas (bagus), bukan memindahkannya.

Solution: Satu modul dalam "pengaturan tampilan toko" (mis. `StorefrontSettings`) dengan interface `get(slug)`, menyembunyikan detail penyimpanan CMS di balik satu seam. 14 kelas jadi 1 modul dalam.

Benefit: Locality naik (konsep "setting toko" di satu tempat); test cukup di 1 interface; perubahan skema CMS hanya di 1 adapter.

SEBELUM (shallow)
14 kelas × getter
repetisi load/page/slug
perubahan CMS = edit 14 tempat
SESUDAH (dalam)
1 modul StorefrontSettings
interface: get($slug)
1 adapter untuk seluruh CMS
STRONG

Kandidat B — Bagi "katalog produk" controller 697 baris

app/Http/Controllers/CatalogController.php (697 baris, 15 method)

Problem: Fat controller menampung render katalog + model + design + filter + rails + flash-sale scope → lemah locality: memahami satu konsep (mis. "kartu model") memaksa membaca banyak method dalam 1 file besar. Interface mengungkap seluruh detail, bukan menyembunyikan.

Solution: Pisahkan render "rak model" (model rails) & "filter katalog" dari controller ke modul/method dalam, controller jadi tipis (delegasi). Interface publik tetap sama.

Benefit: Katalog jadi 1 front yang dalam; logika rails & filter di-test via interface sndiri; controller 697→~200 baris delegasi.

WORTH EXPLORING

Kandidat C — Perdalam "kartu produk" frontend (komponen terpanas)

resources/js/components/public/* (51 file flat) — cart-line-item.tsx 351 baris, 5× berubah

Problem: 51 komponen publik dalam 1 folder flat, paling sering berubah di antara semua (kartu produk, cart-line-item). Kartu & item keranjang berbagi logika harga/opsi tetapi tersebar → shift kecil memaksa touch multi-file.

Solution: Kelompokkan komponen terkait "katalog render" & "keranjang" ke modul berpola (mis. `catalog/` & `cart/`), dengan hook/helper harga bersama sebagai modul dalam.

Benefit: Perubahan harga/opsi produk jadi 1 tempat (locality), UI instant setelah render (leverage).

SPECULATIVE

Kandidat D — Halaman katalog 628 baris

resources/js/pages/Public/Catalog.tsx (628 baris)

Problem: Halaman Catalog besar mencampur state filter + render grid + sort. Perubahan filter merambah bagian render.

Solution: Ekstrak state-filter ke hook dalam (`useCatalogFilter`) agar halaman jadi pembaca, filter jadi modul dalam.

Benefit: Memisahkan data-fetching & render; test state filter tanpa DOM.

🎯 Rekomendasi Utama — Mulai dari Kandidat A

Kandidat A (perdalam 14 *Settings jadi 1 modul) memberi leverage tertinggi dengan biaya sebanding: menghilangkan 13 kelas shallow repetitif pada hot-spot paling intensif (app/Support, 21 perubahan). Ini yang paling "AI-navigable": satu seam CMS yang jelas mengurangi bounce antar modul untuk siapa pun (manusia atau agen) yang menyentuh pengaturan toko.
